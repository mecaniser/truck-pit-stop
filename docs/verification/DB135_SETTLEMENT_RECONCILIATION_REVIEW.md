## Proposed durable evidence contract for Architecture

The current B1 reader trusts a `native` or `reconciled` settlement status plus principal and lineage checks. The proposed reconciliation must **not** merely set `reconciled`: it needs a distinct `db135_reviewed` status and an immutable, same-tenant approval record. Architecture must approve an additive migration after `178_merge_maintenance_bindings` before implementation. Proposed record fields are `id`, `tenant_id`, `invoice_id`, `settlement_id`, `run_id`, `source_envelope_sha256`, `evidence_sha256`, `decision` (`verified_open` or `verified_paid_tender`), `principal_total`, `confirmed_principal`, `currency`, `approved_by_user_id`, `approved_at`, and `created_at`. A unique active `(tenant_id, invoice_id)` key and tenant-safe foreign keys prevent duplicate or cross-tenant approvals. Store receipt contents privately under access control; the database holds only their digest and an operator-visible audit reference. The approval row and financial events must be append-only; a correction requires a new reviewed compensation, not editing the approval in place.

For `db135_reviewed`, `trusted_settlement` must require the approval row, matching tenant/invoice/settlement/customer lineage, principal/confirmed/currency to the cent, no disqualifying paid-baseline event, and a decision compatible with confirmed principal. `verified_open` requires zero confirmed principal and an operator attestation that no known tender/dispute/credit exists. `verified_paid_tender` requires independently verified tender for **all** confirmed principal and no unsupported shortfall; overage is held until its excess is classified. Existing `native`/`reconciled` rows keep their prior trust rules and get separate cohort verification; new DB-135 writes cannot use those statuses. An approval for a prior settlement amount does not certify later unexplained financial changes: the reader must either see a matching immutable approval or the normal native writer's subsequent ledger chain, otherwise return `review_required`. This compatibility and chain rule is an Architecture decision, not yet implemented.

## Required dry run and guarded apply contract

1. Produce a **read-only per-invoice plan** against a new `REPEATABLE READ READ ONLY` snapshot. Keep IDs, money, names, provider references and receipts in a private 0600 artifact; publish only counts, salted/hash references and source hashes. Include source invoice/RO/customer/payment/attempt/ledger/refund/credit rows and the principal from `invoice_money_snapshot`. Include deleted or superseded RO/invoice and bill-to exceptions; no candidate may disappear due to an inner join.
2. For each proposed change, record an explicit evidence decision: `verified_open`, `verified_paid_tender`, `overage_hold`, `shortfall_hold`, or `unresolved`. A reviewer signs the invoice-level evidence and amount, with source receipt reference. The eight overdue rows **cannot** be promoted based on the absence of Payment rows alone. Dry run reports before/after expected native verified subtotal, each aging bucket, unapplied credit and ETS-owned history without issuing any write.
3. Architecture must specify a narrowly scoped, idempotent writer, not invoke `backfill_tenant_invoice_settlements` as-is. That existing tenant-wide routine includes `legacy_paid_snapshot` from `PAID` status, and may create payment attempts/ledger events for unrelated invoices. A B1 writer must select only reviewed invoice IDs, acquire the existing tenant financial advisory lock, re-read all source/identity/settlement rows inside its write transaction, compare the exact source hash, require a still-absent settlement and no conflicting event, and reject any changed or duplicate row. Store a durable `run_id` and per-invoice `source_envelope_sha256`; use deterministic unique `(tenant_id, invoice_id)` and immutable event idempotency keys derived from that run and the source hash. A retry with the same source verifies the existing result; a different source or decision fails closed. Preserve original invoices and payments; no provider call, notification, statement send, credit application, invoice status update or broad tenant backfill.
4. **Apply boundary: one explicitly approved cohort in one database transaction.** The proposal covers exactly the 32 identified invoice candidates, with all 32 disposition records approved or explicitly `unresolved`. An unresolved row is not written and remains outside B1 totals; therefore **full B1 release is blocked** unless every eligible gap is resolved, or the product scope is separately amended. The write set can be a subset of approved rows, but its immutable manifest, source hashes and expected inserted counts are fixed before execution. Acquire the tenant lock, validate the entire manifest, create all specified settlement/approval/event rows, and commit once. Any validation or write failure rolls back the whole write set; no independently committed per-invoice batch is allowed. A later newly approved subset is a separate run, never an implicit continuation of an earlier run.
5. Rehearse the exact plan on a production-shaped **local synthetic fixture**: zero-tender overdue, supported paid tender, overage, shortfall, repeated run, changed source between dry run/apply, tenant mismatch, deleted/merged identity, concurrent financial writer, pending/refunded tender and partial failure. Assert no duplicate settlement/ledger event and no promotion of unsupported principal. Independent QA and Security review the writer, private plan and rollback/compensation procedure. A backup and fixed-cohort hash are taken before any separately authorized production apply; if validation fails, the whole transaction aborts. Reversal must be a reviewed compensating financial action, never a silent delete of immutable evidence.
6. Only after the user separately authorizes the **specific production plan and exact invoice cohort** may Release & Reliability execute it. Re-read source immediately before apply and compare expected hashes; abort on drift. Post-apply verify exact row counts, per-invoice principal/lineage/status, idempotent re-run, fixed-cohort non-target identity and ETS/stock/PM retention. Architecture and independent QA/Security then re-gate B1's complete balance and aging. Protected CI, merge/deploy and authenticated runtime acceptance remain separate.

No production reconciliation, financial/provider mutation or statement delivery has occurred under this proposal. PR #575 remains held at its production coverage gate.
