## Proposed durable evidence contract for Architecture

Architecture conditionally approved a safer direction for implementation: a **B1-only receivable attestation**, separate from `InvoiceSettlement`, instead of a new settlement reconciliation status. The abandoned `db135_reviewed` settlement status would make existing cash/split-payment paths treat an otherwise open invoice differently. An attestation does not change those writers, invoice status, Payment, provider state, credits or the settlement ledger. It is a separately authorized financial **evidence write**, not an automatic backfill.

The proposed additive table after migration `178_merge_maintenance_bindings` records an immutable approval version with `id`, `tenant_id`, `invoice_id`, `repair_order_id`, `customer_id`, `run_id`, `manifest_sha256`, `source_envelope_sha256`, `evidence_sha256`, `decision` (`verified_open` or `verified_paid_tender`), `principal_total`, `confirmed_principal`, `currency`, `reviewer_user_id`, `executor_user_id`, `approved_at`, `valid_until` and `created_at`. A tenant-safe key, unique run/invoice/version and explicit supersession link prevent cross-tenant or duplicate active approval. The reviewer cannot be the executor. Store the underlying receipts privately under access control; the table holds their digest and an operator-visible audit reference, not provider secrets. Approval versions are append-only; correction is a new reviewed version. A short validity limit (proposed maximum seven days) forces recheck of possible offline tender; the exact duration is part of Architecture/Product approval before migration.

The B1 reader may use a current attestation **only if no settlement of any status exists** and the same-tenant invoice/RO/customer lineage, `invoice_money_snapshot` principal, currency and canonical source fingerprint still match. The fingerprint covers invoice status/issue/due/principal/identity plus all linked Payment, attempt, ledger, refund, overpayment and credit evidence; a new or changed source row invalidates the attestation. A later trusted native settlement takes precedence; a new untrusted settlement or any drift makes the invoice `review_required`, never double-counted. `verified_open` requires zero confirmed principal and positive operator evidence of no known offline tender, dispute or credit. `verified_paid_tender` requires proof of every cent of confirmed principal and any excess disposition; a partly supported PAID row remains wholly held. The API and PDF must expose `reconciliation_basis=reviewed_attestation` beside attested amounts so a reviewed historical receivable is not represented as a native settlement. These are design conditions, not implemented reader behavior yet.

## Required dry run and guarded apply contract

1. Produce a **read-only per-invoice plan** against a new `REPEATABLE READ READ ONLY` snapshot. Keep IDs, money, names, provider references and receipts in a private 0600 artifact; publish only counts, salted/hash references and source hashes. Include source invoice/RO/customer/payment/attempt/ledger/refund/credit rows and the principal from `invoice_money_snapshot`. Include deleted or superseded RO/invoice and bill-to exceptions; no candidate may disappear due to an inner join.
2. For each proposed change, record an explicit evidence decision: `verified_open`, `verified_paid_tender`, `overage_hold`, `shortfall_hold`, or `unresolved`. A reviewer signs the invoice-level evidence and amount, with source receipt reference. The eight overdue rows **cannot** be promoted based on the absence of Payment rows alone. Dry run reports before/after expected native verified subtotal, each aging bucket, unapplied credit and ETS-owned history without issuing any write.
3. Architecture must approve the exact additive schema and B1 read rule before implementation; do not invoke `backfill_tenant_invoice_settlements` as-is. That tenant-wide routine can synthesize `legacy_paid_snapshot` from `PAID` status and affect unrelated invoices. A targeted attestation writer must select only reviewed invoice IDs, acquire the existing tenant financial advisory lock, re-read all source/identity/settlement rows inside its transaction, compare the exact canonical source hash, require **no settlement of any status**, and reject any changed or duplicate row. Store durable `run_id`, manifest and per-invoice source hashes. A retry with the same source verifies the immutable result; a different source or decision fails closed. Preserve original financial source rows and all payment paths; no provider call, notification, statement send, credit application, invoice status update or broad tenant backfill.
4. **Apply boundary: one explicitly approved write set in one database transaction.** The proposal covers exactly the 32 identified invoice candidates, with all 32 disposition records approved or explicitly `unresolved`. An unresolved row is not written and remains outside B1 totals; therefore **full B1 release is blocked** unless every eligible gap is resolved, or product scope is separately amended. The approved write set may be a subset, but its immutable manifest, source hashes and expected inserted counts are fixed before execution. Acquire the tenant lock, validate the entire manifest, insert all specified attestation rows, and commit once. Any validation or write failure rolls back the whole write set; no independently committed per-invoice batch is allowed. A later newly approved subset is a separate run, never an implicit continuation.
5. Rehearse the exact plan on a production-shaped **local synthetic fixture**: zero-tender overdue, supported paid tender, overage, shortfall, repeated run, source drift, tenant mismatch, deleted/merged identity, new trusted and untrusted settlements, concurrent financial writer, pending/refunded tender and partial failure. Assert no duplicate attestation, no unsupported principal and no change to payment eligibility. Independent QA and Security review the writer, reader, private plan and rollback/compensation procedure. A backup and fixed-cohort hash precede any separately authorized production apply; validation failure aborts the whole transaction. Correction is a reviewed superseding attestation, never silent deletion.
6. Only after the user separately authorizes the **specific production plan and exact invoice cohort** may Release & Reliability execute it. Re-read source immediately before apply and compare expected hashes; abort on drift. Post-apply verify exact attestation counts, per-invoice principal/lineage/basis, idempotent re-run, fixed-cohort non-target identity and ETS/stock/PM retention. Architecture and independent QA/Security then re-gate B1's complete balance and aging. Protected CI, merge/deploy and authenticated runtime acceptance remain separate.
