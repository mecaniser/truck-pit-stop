# DB-135 legacy receivable attestation contract

Status: **Architecture GO for implementation; no production apply or release approval** (2026-10-18 UTC). Owner: Backend & Integrations; Architecture & API Contracts approved this contract after two returned trust-rule revisions. This is a narrow B1 dependency for native finalized invoices whose historical settlement is absent. It never transfers ETS-owned history, rewrites tender, changes an invoice or payment, sends a statement, contacts a provider, or collects money. The [source review](../verification/DB135_SETTLEMENT_RECONCILIATION_REVIEW.md) is the intake evidence.

## Boundary and decision

An attestation is a time-bounded, independently reviewed **read-model evidence record**, not an `InvoiceSettlement` and not proof that a card/Zelle/cash provider accepted a payment. It may make a historical invoice's **entire** principal and confirmed amount eligible for B1 account display only after source and operator review. The current cash, split-payment and paid-outcome writers remain unchanged. If any settlement (trusted or untrusted) later exists, B1 never uses the attestation: it applies its ordinary settlement trust rules. No automatic ledger event, credit or refund is created by attestation.

Proposed migration: the next available revision after the sole `178_merge_maintenance_bindings` head adds `invoice_receivable_attestations` and `invoice_receivable_attestation_runs`. Before numbering or migration authoring, re-check the live main graph to avoid a collision. Neither table has a cascade that deletes financial evidence. The approval rows are append-only with a version/supersession chain; a supersession never erases the previous decision. Database and service guards must prevent update/delete of approved rows except a separately reviewed migration repair.

Each attestation row binds: UUID `tenant_id`, `invoice_id`, `repair_order_id`, `customer_id`, `run_id`, `version`, nullable `supersedes_id`; `decision` (`verified_open` or `verified_paid_tender`); USD `principal_total` and `confirmed_principal` in cents; SHA-256 `source_fingerprint`, `evidence_digest`, and `manifest_digest`; `reviewer_user_id`, distinct `executor_user_id`, `reviewed_at`, `applied_at`, `valid_until`, and an opaque audit reference. Tenant-safe invoice/order/customer lookup and unique `(tenant_id, invoice_id, version)`, `(tenant_id, run_id, invoice_id)`, and nonnull `supersedes_id` are required. Under the tenant financial lock, the first approval is version 1 with null predecessor; every later approval is exactly predecessor version + 1 and references the current sole head. A competing successor is rejected. The highest contiguous version is the sole authoritative head; an older valid row never becomes a fallback when the head expires or fails review. The run stores exact sorted invoice IDs and source fingerprints privately, public count/digest, expected insert count, authorization reference, reviewer/executor, and `applied` state. Dry run is an external private file, not a `prepared` database row; failed apply rolls back the run and every attestation row. Do not put names, provider references, bank details or private receipt text into API responses or PR artifacts. The exact FK/immutability implementation requires Architecture review.

## Canonical source and eligibility

For each invoice, calculate a versioned canonical fingerprint from same-tenant source rows in deterministic order: invoice identity/status/source/accounting policy, issue/void/cancel/supersession state, billed-customer snapshot, due date and every input to `invoice_money_snapshot`; order identity/customer/source/deletion; resolved customer identity/deletion; **all** linked Payment, payment-attempt, ledger-event, refund, overpayment and target-credit rows, including soft-deleted rows, with amount/status/method/source/timestamps and provider-reference **digests**. A soft-deleted financial child is review evidence and blocks eligibility unless its disposition is explicitly documented; it is never silently filtered. Include row IDs and `updated_at`/deletion markers so a newly inserted, changed or tombstoned source row changes the fingerprint. The fingerprint algorithm, serialization, nullable-field handling and relation limits must be versioned and tested identically in dry run, apply and B1 read. The read path must fail closed at 413 on account/source bounds, never silently omit source rows. Querying source is read-only and tenant-constrained; no live provider lookup occurs on GET.

Only a nondeleted, noninternal, noncancelled, nonvoided, nonsuperseded native finalized invoice with active same-tenant order and customer may be attested. A null pre-155 bill-to snapshot may use the active same-tenant order customer; a nonnull orphan snapshot or deleted order stays review-required. `verified_open` requires confirmed principal zero plus explicit recent operator evidence that no offline tender, dispute, credit, refund or reversal is known. `verified_paid_tender` requires receipt-level proof for **all** confirmed principal and classification of any excess; if confirmed principal is less than invoice principal, it also requires explicit recent operator evidence that the remainder is still due and has no offline tender, dispute, credit, refund or reversal. An invoice marked `PAID` with a shortfall is wholly review-required. `PAID` status and a completed Payment row alone are insufficient; unresolved overage is wholly review-required. `0 <= confirmed_principal <= principal_total` and the principal must equal the current `invoice_money_snapshot` to the cent. An approval expires at most seven days after review. The named Finance/Accounting reviewer must recheck source and operator evidence by day five and approve a new version; Operations runs a daily read-only expiry report. No automatic renewal occurs. Expired or unrenewed heads make the invoice incomplete and block customer statement/collection use. Before release, the board must record the named renewal owner and procedure; absent that owner, the data gate remains NO-GO.

## B1 read and presentation

Inside the existing `REPEATABLE READ READ ONLY` account transaction, load **all** settlement rows for candidate invoices, including soft-deleted and unsupported-status rows, before attestation. A trusted, nondeleted settlement wins and uses the existing `native` basis. A soft-deleted settlement is **always untrusted and blocking**, regardless of its stored status or amount. Any other untrusted settlement also makes the invoice `review_required`, even if a valid attestation exists; there is no attestation fallback. Only with zero settlement rows of **any** deletion state may the sole nonexpired approved head qualify, after verifying tenant/invoice/order/customer lineage, source fingerprint, principal/currency, decision, and approval integrity. If any check fails or a later source row appears, the entire invoice is review-required and contributes neither principal nor aging. For a valid attestation, remaining principal is `principal_total - confirmed_principal` and uses the usual shop-local due-date bucket; zero remains in activity but adds no aging. Add `reconciliation_basis` (`native_settlement`, `reviewed_attestation`, or `null`) to native invoice rows and the PDF, with a clear reviewed-history label. `native.collectible_complete` is true only if all eligible invoices are trusted by a settlement or current attestation and no identity exception remains. Imported ETS totals remain separate. On expiry or failed revalidation, account GET and the PDF route remain read-only incomplete previews with prominent incomplete/review-required labeling; they must never present a complete statement or actionable collection balance. Automated send/collection remains blocked.

## Dry run, apply and safety gates

Dry run uses a new fixed `REPEATABLE READ READ ONLY` production snapshot, emits a private 0600 per-invoice manifest, and computes the exact B1 before/after verified subtotal and five aging buckets without writing. Reviewer signs every approved source/amount/decision; unresolved rows stay held. An authorized executor with a different identity may apply **only the exact reviewed manifest after separate user approval**. In one transaction, acquire the existing tenant financial lock, re-read all 32 dispositions and the approved write set, recalculate fingerprints, assert no settlement of any status and no newer attestation, then insert the run and approval rows atomically. A retry is idempotent only when the manifest digest, every decision, source/evidence digest, principal/confirmed amount, reviewer, executor and authorization reference exactly match the committed rows; otherwise it conflicts and writes nothing. Changed source, changed decision, duplicate key, expired approval, missing authorization or any row failure aborts the entire write set. No partial committed batch. The writer cannot invoke the tenant-wide settlement backfill, a provider, notification, invoice/payment/credit/settlement writer, or a statement sender.

Rehearse migration up/down on a disposable local database; synthetic fixture cases include the eight/24 source classes, exact cents and aging edges, ETS exclusion, null/nonnull bill-to, deleted order, source drift, source insertion after approval, both kinds of later settlement, expiry, reviewer/executor separation, duplicate/retry, tenant mismatch and concurrent payment writer. Independent QA and Security must inspect the final source, private dry-run plan and release/rollback receipt. A production apply needs separate, specific authorization for the exact cohort and its expected financial display change. Post-apply compare source/target row hashes and non-target financial/stock/PM/ETS cohorts. A later correction is an approved superseding attestation, never silent deletion.
