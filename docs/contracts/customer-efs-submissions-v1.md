## Product and existing boundary

EFS only is added beside Card/Zelle for customer and guest invoice payment. No customer Comchek/T-Chek/Other/ACH/general fleet permission is enabled. Customer submits a ten-digit MoneyCode and full/partial invoice amount for shop verification. Submission is not authorization, received money, paid invoice or bank settlement. Shop obtains actual merchant authorization outside this app, then explicitly records verified receipt under existing manual-payment accounting. No EFS provider integration/redemption/search/void API is invented.

Current fleet_payment is staff-only, stores plaintext reference in manual_evidence and checks an unkeyed reference fingerprint at confirmation. It cannot directly hold a customer bearer code or prevent pending duplicates safely. Reuse its manual rail/receipt allocation/account mapping only through the protected EFS source path below; keep historical staff fleet behavior unchanged.

Primary format evidence: [official WEX FAQ](https://www.wexinc.com/resources/blog/fleet-faqs-for-all-your-fleet-management-questions/) and [official MoneyCodes guide p3](https://emgr.efsllc.com/common/pdf/moneycodes.pdf) identify ten-digit codes. V1 accepts trim of OUTER whitespace only, then exactly10ASCII digits, preserving leading zeros. No Unicode digits, embedded spaces/hyphens, PAN/bank account or arbitrary reference strings. Validation errors never echo input.

Body {code:string,amount:decimal-string,expected_settlement_version:int>=1,submitted_for_verification:StrictBool=true}. Idempotency-Key required8–200chars. Browser input autocomplete off and no code in URL.

Success returns existing PaymentAttemptResponse with authoritative settlement plus efs:{provider:"EFS",code_last4:string,status:"awaiting_verification"|"received"|"rejected"|"cancelled"|"review_required",can_cancel:boolean}. Customer history/allocation DTO shows EFS+last4 only, requested amount and verification status. No code/ciphertext/fingerprint/private merchant evidence in public attempt/ledger DTO. No “received” label before privileged receipt commit. Replays return same attempt without duplicate reservation/notification; changed normalized body conflicts. Canonical command hash uses keyed normalized-code fingerprint, amount/version/actor/subject/invoice/provider, never plaintext or an exposed low-entropy SHA hash.

Existing canonical generic customer/guest attempts remain card/Zelle-only; a caller cannot bypass EFS protection with fleet_payment+sender_evidence. Staff generic confirm/fail routes must recognize protected public EFS attempts and delegate/reject according to this contract; guessing a manual reference cannot bypass merchant verification. Historical staff fleet attempts remain supported unchanged.

Staff POST /payments/attempts/{attempt_id}/efs-code/reveal {expected_attempt_version,reason} returns {code,last4} ONLY to exact tenant owner/admin under current payments authority, current authorized invoice/source-collection billed customer and secret/attempt binding. Explicit reveal with immutable actor/time/purpose audit, rate limit, no-store/private/no-referrer, no raw response capture/logging/tracing. No bulk/list reveal. Clear revealed value on close/attempt/access change, avoid clipboard persistence/automatic copy. Reveal does not authorize/redeem/confirm receipt. This scope does not invent a new password step-up requirement; retain any existing applicable sensitive-read policy, and Security independently gates the endpoint.

Staff POST /payments/attempts/{attempt_id}/efs-verification {action:"confirm_received"|"reject",expected_attempt_version,expected_settlement_version,reason,merchant_authorized?:StrictBool,authorization_reference?:string,received_amount?:decimal-string}, Idempotency-Key. confirm_received requires merchant_authorized=true, actual verified received amount and actual merchant authorization/reference distinct from original secret code. This is staff attestation of performed merchant authorization, not an app/provider success claim; audit actor/reference/time. Reject requires reason and no funds may be marked received. Owner implicit/admin existing payments grant only; deny receptionist/superadmin/customer/guest/fleet/driver/mechanic. Current source-collection external accounting restrictions and money guards stay intact.

It cancels only this local request, not the MoneyCode itself. No external void/refund, no paid state and no claim that provider value is restored. Received/refund/dispute evidence denies cancellation. Rejection/cancellation releases ONLY exact reservation once, retains immutable attempt/claim/audit, and displays next step. Customer may retry a different code with a new attempt/current balance/version. Same code is conservatively claimed forever within the tenant, even cancelled/rejected/expired: respond409 efs_code_requires_review with no other invoice/customer details and tell customer to contact shop; no silent code reuse after amount correction. Explicit staff-reviewed future code-reuse is outside V1.

Errors:404 foreign/missing/ownership;422 invalid code/amount/assertion/authorization shape without echo;409 duplicate/claimed code, stale versions, amount unavailable or transition conflict;503 efs_unavailable when dedicated encryption/key material is absent/invalid. Same-key replay reauthorizes current principal before disclosure. No missing-read/failure converted to zero/success.

Use dedicated EFS-purpose versioned Fernet encryption following existing approved versioned crypto pattern. Proposed settings EFS_INSTRUMENT_ENCRYPTION_KEYS (version->Fernetkey JSON) and EFS_INSTRUMENT_ENCRYPTION_ACTIVE_KEY. No hardcoded/derived-from-auth-secret/default production key, no automatic production configuration. Missing/invalid keyring makes EFS unavailable; fictional fixture keys only until separately authorized rollout. Encrypted JSON binds purpose/version/tenant/invoice/attempt/customer/code; decryption validates all bindings. A separately configured stable EFS_INSTRUMENT_FINGERPRINT_KEY supplies keyed HMAC-SHA256 over domain-separated tenant/provider/normalized code for private dedupe. It is purpose-specific, has no default, and is not the auth/OAuth/encryption key. Never publish HMAC or ciphertext. Encryption key rotation leaves the stable HMAC unchanged; retain old decrypt keys while ciphertext claims exist. Fingerprint-key rotation is outside V1 and cannot silently replace the key while claims exist. No key removal/rotation feature is silently added here.

Before insertion, hold tenant financial aggregate lock and refresh exact invoice/settlement/attempt authority, current amount/version and keyring. Check new encrypted claims including pending/rejected/cancelled/expired and old confirmed staff EFS manual_reference_fingerprint computed transiently using existing normalizer; never rewrite old rows or expose legacy references. This prevents reuse of an already received historical staff instrument. New concurrent same-code submissions in same tenant serialize across different invoices/customers and get one claim; different tenant does not disclose global code existence. Database unique index backs same-version race; cross-encryption-version duplicates retain the same stable HMAC and are serialized by tenant. Application must not change keyring inconsistently across Web/Worker; deployment checks include keyring versions/readiness without printing keys.

Raw code NEVER enters manual_evidence, immutable money_snapshot/evidence_snapshot, Payment.reference, provider_reference, outbox payload, notification, PDF/email, customer history, observability, error message, request dump or browser persistence. manual_evidence stores only safe source/provider/last4/sidecar ID. Validation/audit hashes use protected fingerprint, not raw code. Merchant authorization reference is separate; server rejects copying the original secret into that field. Internal reveal is the only plaintext response and is audit-scoped. Do not implement protected source by passing fake masked reference through generic fleet fingerprint (all codes would collide) or by decrypting and then persisting normalized raw evidence.

## Final EFS wire shape

Server derives every action from current actor/invoice/attempt/claim authority and state; customer/guest always receive false for reveal/verify/reject. Frontend must not infer permission from role or existence of a code. can_verify means eligible to submit explicit merchant-authorization evidence, not already authorized/received.

Dedicated submit and verification responses are existing PaymentAttemptResponse extended with required efs:EfsSubmissionSummary and authoritative settlement. Existing allocation rows carry efs:EfsSubmissionSummary|null (nonnull for protected EFS, null for other rails). Combined staff review rows carry efs plus provider_label:"EFS", kind:"canonical_efs_attempt",rail:"fleet_payment". No raw code/ciphertext/fingerprint/private evidence appears in these metadata objects. Staff reveal returns plaintext only through the separately audited exact-attempt reveal response, never through queue/allocation/attempt summary.

Customer EFS cancellation uses existing action cancel_unsent with current attempt+settlement versions, idempotency key and explicit final cancel confirmation/reason. It does NOT use or require the Zelle-only transfer_not_sent_confirmed assertion. Display “Cancel this request” and explain that this does not void the MoneyCode; the code remains claimed here, so retry requires a different code or shop assistance. Server same-claim/permanent duplicate protection remains unchanged.

Private schema refinement approved: sidecar additionally stores fingerprint_key_identity CHAR64, a domain-separated private identity digest of the high-entropy configured HMAC key (never a code digest and never public). Before accepting a NEW submission, query persisted distinct fingerprint-key identities and ciphertext key versions after acquiring the EFS crypto lock. A configured replacement HMAC key while any claims exist, an inconsistent identity set, or unavailable required decrypt-key versions fails closed503 efs_unavailable; no mass decryption, key rewrite, old-claim rehash or inferred recovery. Public wire is unchanged. Encryption rotation with old decrypt keys retained stays independent; changing the stable fingerprint key is not a supported V1 operation.

An EFS crypto advisory transaction lock serializes global first-claim/key-identity readiness and insert across tenants, closing the empty-database race between differently configured instances. Consistent lock order is tenant financial aggregate FIRST, then this one global EFS crypto lock for every path needing both; a crypto-lock-only readiness read must never acquire a tenant lock afterward. Run authoritative identity/version queries AFTER lock acquisition against fresh READ COMMITTED data (or an equivalently proven current serialized view); an older transaction snapshot cannot prove an empty/current key-identity set. Hold lock through claim insert/commit or rollback, no provider/network IO. Normal exact-tenant instrument checks and tenant isolation remain; no global code-existence lookup/disclosure is introduced. Test competing first submissions with different keys/different tenants: at most one key identity commits; the other returns safe unavailable, not a second incompatible claim. Same-key different-tenant submissions remain isolated and safe.
