# Portal booking V1: verified reservation or unpaid visit request

Architecture contract, November 3, 2026. This is the single current contract; no superseded Stripe-only or alternate request-first clauses apply.

User authorizes implementation, isolated tests, design polish, and desktop/mobile preview before deployment. No production booking, provider charge, financial record/configuration change, automatic outreach, refund, or deployment is authorized during this work. Preserve existing invoice, partial-payment and source-debt flows.

## Customer choice and ownership

Immediately after selecting a service, offer **Reserve a time** or **Request a visit** once. Keep that choice through the remaining steps; an explicit change-path control may reset unsent local choices. Reserve requires verified full payment before confirmation. Request is unpaid, reserves no start time and waits for the shop to confirm availability.

Root owns frontend/provider-adapter coordination; backend worker owns schema, ledger, reservation/expiry, request routes and tests. Independent fresh Security/QA own implementation gates. All resources bind authenticated selected tenant/customer and exact authorized vehicle/service UUIDs. Existing operational financial staff roles are owner/admin/receptionist; unsupported roles, foreign/deleted resources and wrong customers fail closed. Staff cannot force paid or confirmed through a success flag.

## Data and accounting boundary

Reservation uses Appointment with `booking_kind='reserve'`, nullable legacy-safe `booking_payment_version=1`, `booking_payment_state`, `hold_expires_at` UTC, immutable price-snapshot hash/version, and nullable confirmed-receipt reference. New payment states: `unpaid_hold`, `payment_processing`, `paid`, `expired_unpaid`, `payment_received_review`, `refund_pending`, `refunded`. Core appointment status stays pending until verified payment plus a valid reserved slot; then confirmed. A reference number alone means neither paid nor confirmed. Legacy rows/statuses/paid_at are not rewritten or re-attested.

VisitRequest is separate: id, tenant/customer/service/optional vehicle, preferred_date nullable DATE, notes, request_reference, status (`requested`,`availability_review`,`withdrawn`), idempotency key/body hash, timestamps. It has **no scheduled_at, slot hold, price, paid_at or provider receipt** and never blocks availability. UI says `Visit request sent` and `The shop will confirm availability`. V1 does not automatically create a reservation from it or send messages.

BookingPaymentAttempt stores tenant/appointment/customer, immutable amount_minor USD, selected provider, account/realm and environment/configuration-version snapshots, provider request/intent/charge IDs, stable idempotency key/body hash, state and proof digests. States include created/creating/requires_action/processing/succeeded/failed/cancelled/outcome_unknown. Enforce one financially live attempt per reservation, unique tenant+idempotency key, and unique provider+account+intent/charge. No PAN/CVC, opaque QBO token, client_secret or raw sensitive provider payload is persisted or logged.

BookingReceipt records exact verified received/refunded minor amounts, currency, provider account/intent/charge, attempt/appointment, verified receipt time, verification basis and immutable proof digest. Unique attempt and provider/account/transaction prevent duplicate money. Immutable events retain actor, versions, provider event identity and proof reference. Tenant-composite foreign keys enforce bindings.

A booking receipt is a **prepaid-service liability**, separate from an invoice sale. Existing Payment.invoice_id is nonnullable: do not create fake completed work, duplicate invoices or synthetic invoice Payment rows to fit it. No invoice/QBO invoice/revenue/tax/marketing-conversion/paid-RO side effect follows from booking confirmation. Expose booking receipt and external accounting reconciliation state separately. Before production enablement, the prepaid-liability accounting owner/mapping or explicit external/manual reconciliation responsibility must be documented; do not silently assign a sales account or mark accounting synced.

## Capability and provider adapters

Support the tenant's **selected eligible QuickBooks Payments or Stripe Connect** provider. QBO is required in V1 because it is an existing tenant rail; Stripe-only implementation does not satisfy that requirement. Server capability validates active tenant, explicit booking admission, existing provider approval/tenant gates, connected account/realm, immutable active configuration version, environment and relevant charging readiness. No global Stripe fallback, automatic alternate provider, fabricated onboarding or inference that invoice approval alone enables bookings. Local source/config defaults do not prove TPS live eligibility.

Reuse lower-level provider clients, tokenization, account binding, signature verification and idempotency techniques. Do not invoke invoice business finalizers, which change invoice/RO/accounting state.

**QBO:** browser card data goes directly to Intuit via existing QuickBooksPaymentPanel tokenization; server receives only opaque short-lived token. Use `quickbooks_payments_service.create_charge(connection,token,amount,description,request_id)` and `get_charge`. Bind immutable realm/environment/configuration/request ID, amount/currency and a stable booking-purpose description/hash. Persist charge ID only from the server's own provider result; never adopt an arbitrary client charge ID. Retrieve under the bound tenant connection; verify actual provider currency, amount, successful capture status, description/request-context proof and persisted attempt binding. Do not default a missing provider currency to USD or invent unsupported provider fields. Validate clientTransID when supported/returned. Existing successful statuses are CAPTURED/SUCCEEDED/COMPLETED only after these checks.

QBO HTTP timeout/429/5xx or unreadable successful response remains outcome_unknown. No new token/request ID/charge while unknown. If ID is missing and the provider offers no trusted retrieval, retain verification/manual-review hold. Tokenization or callback resolution is not payment proof. Existing QuickBooksPaymentPanel's unconditional onToken-success toast must be disabled or use an explicit booking status result for this consumer; ordinary invoice consumers retain their behavior.

**Connect:** create/retrieve the intent in the exact snapshotted connected account and environment, with server amount/currency and metadata purpose `booking_prepayment_v1`, tenant/customer/appointment/attempt IDs and price hash. Elements uses returned connected account/client secret. Verify succeeded, amount_received, currency, account, metadata, environment and stored intent binding. A signed Connect event must match stored provider account/intent, not metadata alone. Dispatch booking events to a dedicated finalizer before invoice event handling; normal invoice events stay unchanged.

## Slot, hold, price and concurrency

Reserve a slot atomically with a 15-minute server UTC hold. Refreshing/back/retry does not extend it. Availability blocks existing confirmed/in-progress appointments plus new unexpired holds and financially unresolved processing holds; legacy pending appointments retain prior nonblocking semantics. Visit requests never consume slots.

Use tenant financial lock before scheduling/row locks, then deterministic tenant/day scheduling keys, appointment, attempt and receipt order. A scheduling lock or equivalent PostgreSQL reservation constraint must serialize overlap check/insertion: check-then-insert without serialization is insufficient. Confirmed/held intervals use UTC instants, include cross-midnight overlaps, allow exact boundary touching and respect returned shop-local 08:00–17:00 slots/duration and DST. Additive TimeSlot fields `starts_at` ISO instant and `timezone` IANA preserve existing `time`/`available`; frontend submits the selected server instant, never reconstructs it in browser timezone. Network provider calls run outside financial/scheduling row locks after durable attempt binding.

Snapshot existing authoritative service pricing once at reservation: full exact positive USD cents, provider minimum, service/tenant/customer/vehicle/slot/duration/price revision/hash. Browser amounts are not authoritative. Later catalogue changes cannot silently reprice that reservation. No partial deposit or free simulated payment in V1; unsupported zero/missing price returns unavailable.

No attempt: expire unpaid hold after 15 minutes and release capacity. GET can calculate expiry without writes; bounded expiry worker persists expiry for new-flow records only. A cancelable unpaid Connect intent may be cancelled under its bound account/idempotency; release only after verified terminal unpaid/cancelled proof. Processing or unknown submitted QBO/Connect payment cannot be assumed unpaid at TTL, blindly resent or refunded. Reconcile stored provider transaction; until resolved show verification pending and protect capacity. A verified terminal decline/no-money result releases the hold. No automatic refund.

Late verified success always creates one real receipt. If hold already expired/released, slot reassigned or appointment cancelled, do not reclaim/move/confirm it: use payment_received_review and `Payment received; booking needs shop review`. Cancellation remains cancelled where applicable. Expiry/success/cancel races run through the same serialized finalizer. Out-of-order failures cannot undo success; refund/dispute evidence is a subsequent immutable fact.

## Frozen HTTP shapes

Money is decimal-cent strings at APIs; immutable minor integers internally. Existing authentication/CSRF conventions remain. Mutations require Idempotency-Key and expected version where shown; same key/body returns original outcome, different body409. Never autoPOST on choosing service/vehicle/time.

- `GET /appointments/payment-capability?service_id=UUID` -> `{available,provider:'quickbooks_payments'|'stripe_connect'|null,reason_code:string|null,message,shop_timezone,currency:'usd',token_url?:string|null}`. Read-only, no booking/intent/charge. Foreign/inactive service404. Request path remains available when reserve payment is unavailable.
- `POST /visit-requests` `{service_id,vehicle_id?,preferred_date?:YYYY-MM-DD,customer_notes?}` -> `{id,booking_kind:'request',request_reference,status:'requested',preferred_date,service_id,service_name,vehicle_id,created_at}`. No financial/appointment/slot side effects. `GET /visit-requests` returns own tenant/customer-scoped paginated envelope.
- `POST /appointments` existing body `{service_id,vehicle_id?,scheduled_at:ISOinstant,customer_notes?}` plus `booking_kind:'reserve'` -> existing AppointmentResponse plus `{booking_payment_version:1,booking_payment_state:'unpaid_hold',hold_expires_at,price_snapshot_sha256,version,currency:'usd'}`. Validate capability/price/slot before reservation; initial state pending, no provider charge. User reviews exact price and expiry before checkout.
- `POST /appointments/{id}/payment-attempts` `{expected_version,price_snapshot_sha256,quickbooks_token?}` -> `{attempt_id,provider,state,booking_status,client_secret?,stripe_account_id?,payment_intent_id?,amount,currency,hold_expires_at,appointment_version,receipt?}`. Server creates/reuses durable bound attempt; commit before provider IO. QBO verified success may finalize immediately. Unknown/processing response permits status checking only, not a new attempt.
- `POST /appointments/{id}/confirm-payment` `{attempt_id,expected_version}` retrieves the stored transaction under its immutable provider identity. It never creates a charge and accepts no client success/amount override. Returns current payment/booking state and real receipt. Confirmed only after full verified receipt and valid held slot. Authorized but missing/unbound proof409; unauthorized404. Legacy blind-success behavior is removed.
- `GET /appointments/{id}` extends with booking/payment state, expiry, safe receipt summary and verification/review note; read-only, no client secret/raw provider data. Polling never charges. The old `/payment-intent` route remains fail-closed unless it delegates to this same Connect ledger; selected QBO never falls back to global Stripe.

Provider browser retrieval and signed webhook success share one finalizer and unique receipt insert. Connect signature/account/event replay protections are mandatory. QBO uses server get_charge/poll/reconciliation; do not assume existing accounting webhook proves a booking charge. Reconciliation retries read stored transactions only. Idempotent provider creation retry after uncertainty is allowed only through proven same-request provider semantics, never a new charge identity.

## Finalization, cancellation and refunds

Finalizer locks/refreshes the exact tenant/slot/appointment/attempt, validates full USD received amount and identity, inserts receipt/event once, then confirms only if reservation remains valid. paid_at uses verified provider receipt time. Missing/partial/processing/authorized-only facts never confirm. Receipt funds and booking status remain distinct when review is required.

Paid cancellation is not a refund. Preserve gross receipt/refunded amounts and audit; signed/authoritative refund events update actual refunded amount idempotently. Pending refund is not zero liability. No automatic refund initiation, forced payment success or historical financial rewrite is in V1. An authorized future operator refund flow must verify provider outcome, including partial refunds and ambiguous outcomes, before updating receipt net amount.

## Required linked-work prepayment hold: no second collection

Before enabling real booking prepayment, deploy a narrow guard for **exact Appointment.repair_order_id** links. No fuzzy customer/name/VIN/amount matching. If any linked new-flow booking has a verified positive receipt not fully applied to the eventual work invoice and not fully provider-verified refunded, ordinary invoice issuance AND new payment collection for that RO must fail409 `booking_prepayment_review_required`. Return safe note `A booking prepayment is linked to this repair. Apply or reconcile it before requesting another payment.` Staff appointment detail shows receipt, gross/refunded/outstanding amount, booking reference and linked RO, with accounting/application review status.

V1 has no automatic BookingReceiptApplication writer. Therefore unrefunded net booking money remains unapplied and held until a separately reviewed application feature or a verified full refund resolves it. Do not clear the hold using a note/status toggle, mark a receipt applied without a ledger, fabricate invoice Payment/customer credit, alter cash reports, or infer refund from cancellation. Future application must use a unique receipt-to-invoice application ledger with currency/tenant/customer/amount checks; it is outside this implementation. Staff can see and resolve the review requirement without silently double-charging the customer.

Compute blocking evidence from tenant-bound linked Appointment+BookingReceipt and authoritative refunded/applications data under the shared financial lock: received>verified refunded+verified applied. Missing/corrupt/ambiguous provider/application evidence holds rather than coerceszero. For actual uncertain booking attempt that might already have captured funds, require verification before a new linked-work charge as well. Unknown outcome must not bypass the guard by leaving paid_at null. Legacy appointments lacking new ledger remain unchanged, not presumed prepaid. No historic rows are seeded or rewritten.

Recommended shared helper `require_booking_prepayment_resolved(db,tenant_id,repair_order_id)` is read/guard-only and called before:
1. `invoices.auto_create_invoice_for_order` and manual `create_invoice`, before invoice/outbox/notification side effects.
2. `invoice_accounting_policy.require_standard_payment` for **new_entry=True** (covers create_attempt/ordinary manual payments), with explicit calls for legacy Stripe/QBO/Zelle/manual compatibility initiation routes that do not use this central path.
3. Any linked-RO reassignment or creation path: adding an existing receipt-bearing appointment link cannot make another invoice's confirmed/pending charge disappear. Detect pre-existing issued invoice/active attempt and hold for review under the same lock; do not retroactively void/refund either.

Do NOT block an already-created provider charge's verified callback/finalization: record real funds once even when a prepayment hold is now present, then flag overlap/manual review. New-attempt prevention and receipt recording are different operations. Existing normal invoice actions on unrelated ROs/customers/tenants remain unaffected.

Before production activation, booking receipt liability must have explicit accounting ownership and this linked-work hold must be verified. Automatic QBO deposit posting/application is not required for isolated implementation preview, but the absence of application automation must be clearly recorded; never activate by pretending that an unapplied prepaid receipt has already settled a repair invoice.
