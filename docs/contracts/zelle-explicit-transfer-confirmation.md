# DB-149Z — explicit Zelle transfer report

Status: FROZEN implementation contract. Architecture owns this file only; Product owns board/frontend and assigns backend. Preview desktop/mobile before deployment. No production invoice/payment/attempt edits, real transfer, notification delivery, provider action or retrospective cleanup is authorized.

## Findings and meaning

SettlementPaymentPanel currently calls createPaymentAttempt before showing Zelle instructions. create_attempt immediately inserts a pending attempt, reserves principal and appends ledger evidence. Canonical portal POST /payments/invoices/{invoice_id}/attempts and guest POST /invoice-access/attempts do not stamp Invoice.zelle_pending_* or invoke staff submission alerts. Dashboard pending-Zelle lanes read that legacy timestamp, so canonical attempts can be pending without the existing staff signal.

Legacy /submit-zelle routes already mean “customer reports sent”: they stamp queue fields, bind compatibility_submitted_at into attempt evidence, dedupe and enqueue eligible SMS transactionally, commit, then attempt email and optional direct SMS best-effort. Email exceptions are swallowed; that is not durable email delivery. SMS outbox is durable only when configured/enabled and an eligible destination exists. Never claim every shop email/SMS was delivered. Durable internal pending-review visibility is required independently of delivery.

A report means only “customer says this transfer was sent.” It is not verified receipt, settled money, invoice payment confirmation, revenue, provider authorization or accounting success. Shop verification remains the existing privileged confirmation flow.

## Frozen frontend boundary

Choosing Zelle / viewing instructions is local read-only UI. Snapshot validated positive selected principal, summary version, recipient identity and customer-facing invoice memo; preserve existing full/partial amount selection. Show recipient/amount/memo copy controls without POST, pending reservation, legacy timestamp, ledger or notification. Back changes local UI only. No automatic attempt creation from selection, mount, copy, instruction open, refresh or retry of a read.

Final action label “I've sent the payment” explicitly reports the transfer. Require the user's explicit confirmation, then submit transfer_sent_confirmed:true. Use one stable idempotency key for that exact amount/version/recipient/transfer-report intent; uncertain failure retries use the same key, never generate a new one per mutation retry. Disable duplicate submits. Changed invoice/customer/access, amount, recipient or summary version invalidates the draft before submission and requires updated instructions/confirmation. Do not silently submit stale recipient instructions. Server settlement/version checks remain authoritative.

Success says “Transfer reported” / awaiting shop confirmation, not “Follow instructions”, “paid” or “received”. Customer has one semantic pending notice and one pending amount. Remove redundant pending badges/headings/paragraphs across shared panel and portal/guest parent; payment activity may be collapsed with accessible controls. Partial-payment balance remains accurate. Refresh is scoped read-only settlement/allocation reads with visible loading plus updated/no-change/error feedback, no attempt creation, provider reconciliation, receipt claim or blanket success on failed reads. Preserve last valid data while showing error; no false-zero balance. Tenant/access-bound responses cannot overwrite another invoice's state.
