# Booking fulfillment and prepayment application — FROZEN IMPLEMENTATION CONTRACT

Status: FROZEN IMPLEMENTATION CONTRACT. Implementation is in progress; not production-ready. Owner: Product & Delivery Lead; Architecture owns this contract. No production record, provider, configuration, or notification changes are authorized by this document. Independent Security and QA must review implementation. Existing production booking gates remain off.

## Evidence and boundary

`VisitRequest` currently supports requested, availability_review, withdrawn; staff GET is not fulfillment. It has no reviewed scheduling transition or staff action UI. New BookingReceipt is a prepaid liability, not an invoice Payment. Appointment.repair_order_id exists, but no audited new-flow link/application writer exists. The exact-linked-RO invoice guard correctly rejects unresolved funds; it must not simply be removed.

`invoice_settlement_service.apply_customer_credit` requires a PaymentOverpayment backed by a confirmed InvoicePaymentAttempt, source invoice and versioned accounting configuration. It emits customer_credit.accounting_sync. Booking receipts have none of that provenance. Do not manufacture these records to reuse that function. Existing invoice paid webhooks/outbox and invoice projections must consume a genuine new application event.

## C. Immutable prepaid application, without another charge

Add BookingReceiptApplication: id, tenant_id, receipt_id, appointment_id, repair_order_id, invoice_id, settlement_id, customer_id, amount_minor positive integer, currency USD, receipt/provider/configuration/account/realm snapshot hashes, actor, timestamp, idempotency_key and canonical request_hash. Composite FKs bind tenant and exact identities. Append-only events, no edits/deletes; future reversal is a separately authorized compensating entry, not deletion. Unique tenant+idempotency key. No Payment, PaymentOverpayment, InvoicePaymentAttempt, second provider charge, or fake customer-credit origin is created.

Available booking liability = verified receipt gross minus verified provider refunds minus committed applications (plus explicit committed reversals). Unknown provider/refund/dispute outcome freezes new application. Partial application is allowed only up to both available liability and allocatable invoice principal; fees are not charged again. Receipt must exactly match confirmed provider account/environment/currency/amount/intent and frozen booking provenance. Preserve excess as unapplied booking liability with visible amount, not revenue. Full original receipt remains in cash receipts exactly once at received_at; application is zero new cash.

The current issuance guard means issuance and application need one atomic dedicated operation: POST /appointments/{id}/issue-invoice-with-prepayment {repair_order_id, receipt_id, amount_minor, expected_booking_version, expected_receipt_version, invoice_options}, Idempotency-Key. Reuse ordinary issuance calculations/checklist/tax/discount/number allocation in a transaction-local service, but do not publish/commit/notify before application succeeds. This capability is narrowly internal to the operation, not a caller boolean bypass. It creates the genuine sale invoice once, applies only to its principal, appends settlement event booking_prepayment_applied, increments version, updates paid/partial presentation through existing settlement rules, then publishes one final invoice/outbox state. Failure rolls back invoice+application+events. Repeated request replays same invoice/application. Existing draft/issued target needs a separate reviewed exact-target application endpoint with expected settlement version; no arbitrary customer-credit transfer.

Guard evolution: allow ordinary collection only after exact eligible applications/refunds fully dispose of linked liability and no uncertain attempt remains. Invoice issuance through the dedicated atomic operation is allowed only for the selected receipt, same exact appointment/RO/customer and validated residual; all ordinary issuance paths remain protected. If unapplied excess remains, staff must resolve it through explicit refund/liability review before another collection, not silently lift hold.

Accounting: receipt arrival debits provider clearing and credits booking-prepayment liability, not sales/tax. Application debits that liability and credits the issued invoice A/R; invoice issuance recognizes its actual sale/tax once under existing accounting policy. Provider fees retain original receipt attribution and are never charged/exported twice. Introduce dedicated accounting object/event with unique immutable application operation ID, tenant versioned realm/account mapping, and one owning writer. Do not feed unsupported booking events into existing customer-credit handler. No production enablement until the selected tenant writer can represent both liability receipt and application, or an explicit externally reconciled mode has durable review acknowledgment and financial-export holds; pending is never labelled synced. The actual mapping/operational authority is a rollout prerequisite, not an inferred bank fact.

Refund/cancel: no automatic refund policy is inferred. Before application, a verified full refund releases liability; pending/unknown stays held. After application, block original booking refund from exceeding unapplied amount; invoice-linked refund/reversal requires its dedicated accounting-safe compensating flow. Cancellation does not erase receipt/application, alter paid history, create revenue, or claim refunded. Provider late success always remains a receipt needing review if capacity is gone.
