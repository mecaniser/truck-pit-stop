# DB149R — frozen booking readiness contract

Status: FROZEN for source implementation and independent verification. Owner: Product & Delivery Lead. Architecture owns this contract; backend implementation is separate. Branch: codex/booking-readiness-legacy-mirrors, baseline8ae33bd3. Approved UI stays unchanged. This contract authorizes no production record/config/provider/env changes, token refresh, financial backfill, charge, refund, activation or external bookkeeping acknowledgment.

## Decision and evidence

Booking eligibility must use fresh read-only readiness for the exact persisted immutable provider configuration. TenantPaymentProviderConfiguration.readiness_state is the historical result calculated when that snapshot was inserted; it is not a separate administrator disable switch. Active/deleted state, exact version/provider/account/realm/mappings/writer and all platform/tenant/environment gates remain authoritative. A historical not_ready value must not permanently veto a currently valid configuration; a historical ready value must not override a current failure. Do not edit configurationv1 or insert a syntheticv2 only to update this derived status.

Both booking_provider_capability and _bound_configuration(new_charge=True) currently test the stored readiness_state. Both must call one shared fresh evaluator; fixing capability alone would display a working Reserve path whose checkout still fails. Existing invoice provider_readiness is read-only and evaluates backfill/provider/accounting mapping gates without initializing settlements or replaying financial history.

Merged446b87d4 already uses billed_customer_id for source_collection_hold settlements and payment attempts via CASE; ordinary invoices use RO.customer_id. Do not replace this with an unconditional original RO customer predicate. The reported collection mismatch from an approximate diagnostic is not evidence that the current code lacks this CASE. Existing source_handoff validation is still required to establish collection bill-to authority.

## Narrow tenant-wide mirror exclusion

Only when invoice_id is None, the missing-settlement invoice prerequisite excludes a proven raw ETS mirror: Invoice.source='easy_truck_shop_import' AND its exact joined RepairOrder.source='easy_truck_shop_import', with Invoice.tenant_id==RepairOrder.tenant_id==requested tenant and Invoice.repair_order_id==RepairOrder.id. Both markers are required; a single imported-looking marker, other source or native invoice remains subject to existing rules. NULL source values must behave as ordinary values, not disappear through SQL three-valued NOT logic. Do not exclude by status, number prefix, paid label, source balance, arbitrary ID allowlist, customer or broad historical accounting policy.

The exclusion is only from tenant-wide missing-settlement readiness. It does not make a mirror payable, grant portal/fleet/finance access, enroll it in QBO, create a settlement or alter its invoice/RO/accounting status. A directly requested raw mirror fails closed with a read-only/unavailable reason even if it already has a stray settlement. Preserve all ancestry checks, including imported predecessors, rather than allowing the tenant-wide skip to hide predecessor money. This direct-denial is explicit and does not depend solely on absence of a settlement.

Ordinary native invoices remain in the prerequisite; missing/wrong-tenant/wrong-customer/deleted settlements still block. Native source-collection copies remain in scope with the existing CASE payer logic, reviewed exact handoff/native/source/customer authority, active state and source-proof checks. Reuse source_debt_handoff invoice_handoff/effective billing authority for actual collection admission; no global relaxation of RO ownership. Do not blindly reuse accounting export admitted_invoice_predicate to classify collection payment readiness: collection copies intentionally have a distinct external accounting policy.

Unreconciled Payment, pending Zelle, source proof, replacement ancestry, latest verified backfill, account mappings, writer strategy, provider approval, tenant isolation and all unrelated readiness reasons are unchanged. In particular, real native payment activity on imported lineage is NOT exempted merely because the mirror itself does not require a new settlement. Do not alter verified backfill history/cutoff/checksums or manufacture a new verified run. Tests prove existing blockers remain independently effective.

## One shared fresh booking evaluator

Implement one private read-only evaluator used by capability and new-charge binding. It accepts the exact tenant and exact persisted configuration already selected/bound; it does not silently substitute whichever provider/configuration is now active. Reload mutable authority columns with populate_existing so a cached ORM instance cannot retain old is_active/readiness/connection state. Require the supplied configuration's tenant/version/provider/account identity to match the persisted active nondeleted row, the tenant active/nondeleted, and writer_strategy='dieselbridge'. Invoke provider_readiness(db,tenant,config=that_exact_config) explicitly and require its CURRENT status=='ready'. No stored readiness_state string is sufficient or necessary for this derived decision.

Use an explicit no_autoflush boundary for readiness reads so unrelated pending ORM edits cannot be flushed as a side effect. The fresh evaluator performs no add/flush/commit/update, get_or_create_settlement, backfill, OAuth/network request, token refresh, accounting task acknowledgment or outbox mutation. Existing locking/source-read behavior stays read-only. There is no new readiness cache, background persistence or permission bypass.

Capability still requires BOOKING_PAYMENTS_ENABLED, approved exact tenant and admitted provider environment. QuickBooks still requires platform approval, original connected company, matching configuration provider-account AND QBO-realm snapshots, payment OAuth scope, actual unexpired access and refresh tokens, environment admission and exact environment. Stripe still requires approved connected-account onboarding, webhook secret, exact account snapshot and admitted environment. Full existing provider_readiness account mappings/verified backfill/writer gates are retained for either rail. No global Stripe fallback and no selection of a different provider/account to make the response green.

At _bound_configuration(new_charge=True), re-evaluate fresh readiness against binding.tenant_id+configuration_version+provider+account_id and the same current environment, then retain all existing create_booking_payment provider/token/metadata/price checks immediately before provider submission. An inactive or replaced bound version must fail; do not rebind an existing reservation to a newly active version. Preserve existing recovery/retrieval validation for new_charge=False: it must continue recording verified facts under the original immutable version/account/environment after admission is disabled or the configuration replaced. Historical not_ready/ready snapshots are still audit data, not modified or backfilled.

Do not add a token refresh to the read-only evaluator. If OAuth is expired, capability remains unavailable until a separately authorized normal credential-refresh workflow succeeds. A code correction alone does not change environment flags, credentials, stored configuration or financial rows. Deployment and production activation are separate decisions; read-only activation evidence must pass before changing any existing gate.

## Frozen acceptance and negative matrix

1. A tenant with only coherent raw ETS mirrors lacking settlements can pass the missing-invoice prerequisite after all OTHER current readiness conditions pass. Raw mirror paid/sent statuses are irrelevant; exact 401-row production observations are diagnostic evidence, not a hard-coded test/allowlist. Every row and source status remains unchanged.
2. Same invoice/RO tenant binding is mandatory; foreign RO, single-marker or native/NULL-source invoice is not silently excluded. A missing native settlement blocks. Wrong customer/tenant/deleted settlement blocks. Source-collection native copy with correct reviewed billed customer remains in scope and can pass even when original RO customer differs; invalid/missing/inactive handoff or forged bill-to authority stays blocked by actual admission.
3. Direct raw-mirror request is explicitly unavailable, with and without a settlement, no new settlement/payment creation. Ordinary and collection invoice-specific flows retain existing gates and ancestry/money checks. Imported predecessor money remains blocking.
4. Unreconciled completed/refunded native Payment, pending/mismatched Zelle, unverified/stale backfill, bad mapping, wrong realm/account, unsupported writer, provider/platform gate off, tenant gate off or ancestry conflict independently defeats readiness. No unrelated reason is suppressed by the mirror correction.
5. Persisted active configv1 snapshot not_ready + genuinely fresh ready permits capability AND bound new-charge validation in disposable provider-boundary tests. Snapshot ready + fresh not_ready denies BOTH, and makes zero provider calls. Different/deactivated/deleted/replaced version, stale cached active flag, wrong tenant/provider/account/realm/environment all deny. No configuration row is mutated or newly inserted by these reads.
6. Expired access or refresh token, missing OAuth scope, absent secret/onboarding, unapproved tenant/provider/environment or booking flag off stays unavailable with zero network calls. Readiness never refreshes tokens automatically. Verified provider retrieval/finalization remains allowed for its original binding as before.
7. Tests include actual SQL tenant-cohort classification (especially NULL source semantics), matching environment focused provider/readiness suites and actual PostgreSQL isolation when available. Record DB new/dirty/deleted state and protected financial table fingerprints before/after reads. No real provider submission; synthetic boundary fixtures only.
8. Independent Security and QA review source and exact tenant negative cases. Re-run relevant critical tests, migration graph (no migration expected) and changed runtime GET/capability flows after source freeze/runtime alignment. Approved UI is unchanged. Report code, merge/deploy, read-only readiness, credential/gate activation and actual payment as separate evidence; no capability success is proof of a payment.
