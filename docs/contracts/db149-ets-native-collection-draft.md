### Stage C — two directional receipt workflow

**DBN → ETS manual task:** A real confirmed DBN receipt creates exactly one durable `ets_receipt_update` task in the same DB transaction as its local application. Fields bind tenant/debt/native invoice/attempt/payment IDs, confirmed received/principal/fee/unapplied amounts, currency, effective date, receipt reference, expected source revision and a stable task key. States: `pending_manual`, `claimed`, `awaiting_verification`, `verified`, `conflict`, with immutable actor/time/evidence events. Only confirmed principal belongs to the ETS invoice allocation; optional DBN processor fees and unapplied funds must not silently be posted as ETS repair debt. Partial payment requires recording the exact allocation in ETS, not marking the whole invoice paid. Fully settled DBN debt may be marked paid only after the corresponding source allocations are verified. Task creation does not mean ETS is updated; UI says `ETS update pending` until fresh exact source allocation/read-back proves it. `Done` buttons alone cannot assert `synced`.

The operator performs ETS entry using its normal UI. DBN acknowledgement supplies exact source allocation ID(s), amount and evidence/source revision; server verifies fresh complete source read and maps each DBN principal receipt to the corresponding source allocation once. Exact amount/date alone is insufficient because two legitimate receipts can share both. Ambiguous read-back stays awaiting verification/conflict. Claim expiry never auto-reposts or duplicates an ETS entry. Completed tasks retain source receipt identity permanently. A manual ETS field change that creates no attributable allocation is insufficient to verify a receipt; hold for review rather than infer a payment.

**ETS → DBN external receipt:** Ingestion keys immutable source allocation by `(tenant, ETS shop, source invoice internal ID, source payment allocation ID)` plus observed revision; DB unique constraint and body hash guarantee exact-once application. It first checks DBN→ETS task mappings: an ETS allocation acknowledging an already-recorded DBN payment only completes that task, and must NOT create another DBN Payment/application. A distinct verified ETS receipt creates an external-source receipt/application for the existing canonical native debt with its source origin and original effective time. It never calls a card/ACH provider or sends a payment request. If allocation identity is missing, reused with changed value, or could match an unacknowledged DBN receipt, record observation and conflict only. A source status flip alone is not enough evidence to fabricate a receipt.

External receipt application and source task acknowledgement share the tenant financial lock and debt revision with native attempts. Apply actual received facts once; amount beyond remaining principal becomes explicit unapplied/overpayment evidence requiring normal resolution. Never cap and discard money, silently refund, or rewrite original source allocations. Source refunds, reversals and edited/deleted allocations become immutable reversal/reconciliation work, not deletion of previously confirmed receipt history.

**Accounting/outcome deduplication:** A mapped ETS acknowledgement never creates another payment, export, tax event or conversion. A distinct ETS receipt is recorded as external-origin money; its accounting ownership is ETS/external writer unless an explicit future policy designates otherwise. Exclude it from native provider/QBO payment re-export and native paid outcome export. Distinct DBN receipts retain their own provenance; while manual source/QBO application is pending, display accounting reconciliation pending, not synced. Both directions map to the same original debt; report payment once and do not recognize transferred opening balances as new revenue/tax. Designated accounting receipt writer must acknowledge original QBO allocations without creating a second invoice. Existing DBN accounting writers require transfer-aware admission rather than bypassing historical policy.

### Reservation and race behavior

Activation requires a fresh exact-source read after the owner acknowledgement. After activation, DBN is the primary balance ledger: before enabling an attempt, reconcile every already-observed unmapped source allocation, check source-monitor health and all conflict/uncertain-provider holds, and reserve the native allocatable balance under the tenant lock. Store the last reconciled source revision with the attempt. The proposed source-monitor health window is at most24hours, matching the existing reader freshness ceiling; a failed latest read or unresolved source identity/payment conflict blocks new attempts until refreshed, while confirmed DBN receipts remain valid. A remote ETS read is not required inside each DB transaction, and the source’s stale original balance never overrides the active DBN balance. Collector/manual refresh occurs outside financial locks. Freeze the exact health threshold with operational evidence before implementation; no arbitrary freshness value becomes financial truth. Source collection can still happen after that read: no distributed exactly-once guarantee is claimed. Operator must avoid concurrent ETS collection for the debt while DBN has an active reservation; observed exception moves it to conflict and stops new collection. Do not cancel or resend an uncertain provider charge. Confirm provider fact, record source fact, then route overlap to existing overpayment/refund/manual resolution. A DBN receipt awaiting ETS acknowledgement is already locally paid, so stale ETS balance must never reopen DBN debt or create another payable document.

Manual ETS task backlog is a separate synchronization state from invoice payment state. A paid DBN invoice can truthfully be paid while `ETS update pending`; that pending task does not justify taking another payment. A distinct ETS receipt should reduce native remaining immediately after verified exact-once application even if manual accounting acknowledgement remains pending.
