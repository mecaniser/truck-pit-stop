Status: FROZEN implementation contract. Baseline origin/main e3936844, branch codex/payment-attempt-resolution. ## Findings and decisions

Current fail_attempt releases any pending attempt, including card, without provider no-charge proof; generic staff /fail is broader than canonical money permission. Stripe intent-creation error currently routes any StripeError to fail_attempt, including ambiguous timeout. QBO charge uses immutable db048-attempt-{attempt UUID} request ID, but lacks a committed pre-IO submission marker. Therefore missing provider ID, elapsed time, empty customer browser state or missing old ledger marker does NOT prove that an existing card request was never submitted. Card expiry already avoids blind local release and must remain safe. Legacy financial/ancestor evidence is not rewritten or newly trusted.

Resolution cancels an exact local request/reservation, not a bank transfer or received money. Zelle assertion is not verified receipt. Card checkout-started, submission-started, provider-verified receipt and terminal no-charge are distinct. Preserve existing actual-received allocation, underpayment, overpayment/refund/credit rules. No cancellation rewrites received amounts, deletes attempts, modifies old ledger evidence or marks an invoice paid/unpaid as a shortcut.

## Additive API freeze

Authenticated mutation path POST /payments/attempts/{attempt_id}/resolution and guest equivalent POST /invoice-access/attempts/{attempt_id}/resolution records a command. Read projection is additive resolution metadata on existing allocation rows, not a second parallel GET/pending list. Guest token is provided through the existing invoice-access token mechanism/body, never embedded in staff links/logs. No mutation on GET, refresh, panel mount or dialog open; use no_autoflush and pre-existing rows, never settlement initialization.

POST body: {action:"cancel_unsent"|"check_provider_status"|"request_review"|"release_with_terminal_evidence",expected_attempt_version:int>=1,expected_settlement_version:int>=1,reason_code:string,reason?:string,evidence?:TerminalEvidence}. Require Idempotency-Key. Cancellation dialog confirms “This cancels the payment request here. It does not cancel a bank transfer.” Customer Zelle cancel requires strict boolean transfer_not_sent_confirmed:true; staff must explicitly select “Payment not sent” with nonblank reason and the same assertion. Card cancel does not use this Zelle assertion as provider proof. POST cannot change rail/provider/account/amount/customer or supply a new payment token.

DTO: {attempt_id,invoice_id,attempt_version,settlement_version,rail,requested_principal,currency,attempt_state,checkout_status:"checkout_started"|"transfer_reported"|"verification_pending"|"review_required"|"received"|"cancelled"|"failed",reservation_amount,can_retry:boolean,actions:{cancel_unsent:boolean,check_provider_status:boolean,request_review:boolean,release_with_terminal_evidence:boolean},block_reason:null|{code,message},resolution_notice:null|{kind,message,resolved_at},review_status:"none"|"requested"|"evidence_required"|"resolved",settlement:<existing audience-shaped summary>}. Money strings reuse current USD precision. The server derives actions/status from authoritative evidence, not client guess or display label. No card/bank secrets, unmasked staff evidence, merchant case documents, internal failure traces or guest tokens in public DTO. Staff detail may additionally expose exact immutable provider binding/request ID and authorized evidence review history. Existing PaymentAllocation rows include resolution:<this audience-shaped DTO> and mutation returns existing PaymentAttemptResponse with resolution plus updated settlement. Batch immutable evidence reads for each allocation page; no per-row network calls/N+1. Customer/guest existing identity-bound allocation request is the read source; no separate GET is required.

GET invoice/allocations must still display terminal resolution history after the active panel disappears: e.g. “Payment request cancelled. No payment was recorded. You can try again.” A received/late receipt overrides the current financial interpretation; preserve the historical cancellation event while showing actual money/review. No UI “cancelled” claim based solely on a closed checkout dialog.

Errors:404 foreign/not-owned/missing;422 missing strict assertion/reason/evidence shape;409 stale_attempt_version/stale_settlement_version/idempotency_conflict/attempt_resolution_not_allowed/provider_outcome_unknown/provider_review_required. Unknown provider result may return an authoritative pending/review DTO with an explicit pending result; never a success/cancelled notice. Same key+same normalized command replays without duplicate ledger/reservation/IO; changed command body conflicts even if attempt already terminal. Reauthorize before replay disclosure. Preserve the original expected versions in request hash; replay detection precedes fresh-version rejection. Different key against terminal attempt returns explicit conflict/current DTO, never silently treats an unrelated cancellation as successful.

## Authorization and exact scope

Customer: active authenticated tenant/customer with existing invoice_customer_access authority, exact attempt.customer_id == effective billed customer and same settlement/invoice/tenant. Resolve reviewed source-collection authority through existing invoice_handoff helpers, not raw RO customer. Guest: valid unexpired invoice token, exact invoice/customer/tenant scope and existing attempt/token ownership rules. Token rotation/another invoice/foreign tenant cannot cancel or inspect the attempt; no guessed UUID access. Staff: owner implicit, garage_admin with current payments permission, same tenant and current canonical can-manage-money authority. Deny receptionist/superadmin/mechanic/fleet/driver and arbitrary permissions JSON bypass. Existing step-up requirements for money-management/manual review remain; human terminal-evidence release is an explicit privileged decision, not a customer capability.

Customer/guest can cancel only their own eligible manual Zelle report/request or proven safely cancellable card checkout. An attempt created by staff is not self-cancellable merely because it belongs to the customer's invoice unless the existing subject ownership binds it to that customer and action is explicitly allowed. Staff may review exact customer/guest/staff attempts under invoice authority. No broad customer-level cancellation, invoice-wide fail, or release of another rail/attempt.

## State/ledger contract, no migration by default

Reuse InvoicePaymentAttempt pending/failed/expired/confirmed/refunded/reversed plus existing immutable InvoicePaymentLedgerEvent.evidence and versioned settlement. Represent cancellation as terminal failed with an explicit stable cancellation failure_code and immutable attempt_cancelled event; public checkout_status=cancelled is derived from that event, not a new received-money state. Resolution commands/audit records include normalized request_sha256, actor identity/role, subject, exact IDs, expected/resulting versions, reason, pending delta, proof kind and provider binding snapshot. Enforce ledger uniqueness by tenant+resolution command key using existing event constraints. A dedicated small schema extension is allowed only if existing immutable evidence cannot safely represent the required protocol; freeze it with Architecture before implementation. Do not mutate manual_evidence after attempt insertion merely to add a review marker.

One financial transaction locks tenant aggregate first, then refreshes exact invoice/settlement/attempt plus relevant ledger/refund/dispute rows with populate_existing and row locks in existing canonical order. Validate principal/customer/tenant/provider bindings, expected versions and current state after locking. Pending release subtracts ONLY this attempt's still-reserved principal, exactly once; do not clamp an inconsistent aggregate to zero. Inconsistent reservation amounts require review. Increment attempt and settlement versions once, append one resolution event, recompute existing settlement state. Other card/Zelle reservations, confirmed principal, actual receipts, invoice economics and reviewed accounting/source policies remain intact. Transaction rollback leaves no partial release/audit. Existing booking-prepayment, source-collection, historical invoice and revised-ancestor guards remain effective; new resolution evidence must not broaden reviewed_test_ancestor eligibility.

## Zelle cancellation and future late money

Eligible pending Zelle request/report with no confirmed receipt can be cancelled by its authorized customer/guest after “not sent” assertion or by money staff after explicit reason. Release reservation locally and show “Request cancelled”, never “Zelle transfer cancelled”. Preserve sent-report/customer assertion and subsequent cancellation as separate immutable facts. No bank API, refund or external source-paid action is called. Already confirmed/refunded/reversed or inconsistent receipt/credit/refund/dispute evidence cannot be cancelled. Existing older requests remain untouched unless a user explicitly resolves that exact eligible row.

Legacy invoice flags are not generic release controls. Canonical attempt cancellation must not use legacy /zelle-pending/revert or clear unrelated invoice-level submissions. If a matching compatibility projection exists, update it only through an exact existing proven marker/attempt match and only if no other unresolved report uses it; otherwise leave it and surface review. Never delete historical evidence. Staff canonical review/cancel must continue opening StaffSettlementDialog(invoiceId) with exact attempt, not full-invoice legacy confirm.

Late verified money after local cancellation is retained via existing privileged genuine-fact confirmation path. User assertions cannot manufacture that proof. Reacquire locks and apply actual receipt against current allocatable principal; any excess/unapplied/fee/refund/credit follows existing canonical rules and remains visible for review. Do not discard actual receipt because attempt was cancelled/expired, silently double-apply invoice principal or automatically repeat a charge. Source-collection external acknowledgment remains separate. Customer and staff histories show the real receipt/current balance plus prior request cancellation.

## Card dispatch protocol and cancellation

For NEW protocol attempts only, append immutable card_submission_protocol evidence with version1 and exact provider/account/configuration/environment/request identity at creation. Before ANY provider operation that can create or submit a payable object/charge, serialize against cancellation, recheck pending/current versions/binding and COMMIT a card_submission_started event. This durable marker is before external IO, not only in exception handling. A crash after the marker means possibly submitted and stays reserved. Missing marker proves unsubmitted ONLY when new protocol evidence exists and ALL dispatch entry points honor it. Historic no-ID/no-marker attempts are unknown, not automatically safe. Stripe intent creation itself crosses this boundary; a client secret issued to a browser can still be used later unless the provider intent is terminally cancelled.

Local card cancel is allowed only for a new-protocol pending attempt with no submission-start marker, no provider intent/charge/reference, no received money/refund/dispute/accounting fact and no active dispatch/reconciliation owner. Under the same tenant/row serialization, terminalize locally; dispatcher must reject its old attempt/version before IO. This covers checkout opened but not submitted. UI tokenization or browser closure alone is not proof. The existing QBO immutable request ID remains stable; no new idempotency key/retry token may cause a second charge of an unknown old request.

Known provider ID: check_provider_status uses existing account/environment/config-bound provider GET and existing proof/amount/currency/metadata rules. Genuine succeeded/captured/received money enters existing verification/receipt pipeline, not fail. Processing/requires_action/unknown/mismatch/refund/dispute remains reserved/review. Provider terminal FAILED/DECLINED/CANCELLED is releasable only where the provider adapter explicitly proves no capture/authorization can later settle. Do not infer terminal no-charge from arbitrary status names or HTTP404. Reuse existing verified provider status policy and fixtures; no speculative QBO request-ID search API.

Stripe cancel: when supported by existing Stripe API/adapter, explicit cancel_unsent may cancel a bound eligible uncaptured PaymentIntent, followed by authoritative retrieval of canceled state before local release; server validates connected account/environment/intent metadata/amount and serializes versus webhook confirmation. A succeeded/captured intent is not cancelled/refunded by this action. Timeout/ambiguous cancellation keeps hold. No new QBO refund/void command is invented: known QBO charge remains check/review unless supported terminal no-charge proof exists. Staff must not choose “not sent” to override a possibly submitted provider request.

All generic /fail routes, background expiry, intent-creation errors, provider error handlers, staff manual paths and source adapters must call the same authoritative release policy. A caller failure_code/expired=true is NOT proof. No generic staff endpoint or service-only invocation can release a card with unknown/provider-bound outcome by bypassing the new route. Definitive provider rejection may use an internal validated proof object, scoped to exact tenant/attempt/provider/result; never expose a caller boolean verified=true. Ambiguous Stripe create errors/timeouts preserve reservation instead of current unconditional fail. Existing manual-rail expiry stays separate; card local timeouts never release automatically.

## Missing-reference staff review — usable, evidence-backed

request_review records a durable immutable review_requested event (idempotent exact attempt) with reason, visible in existing staff payment review surface even after browser refresh; no release. UI shows “Payment needs shop review”, exact amount/attempt/provider binding, requested time and safe next steps. Staff can attach a KNOWN provider reference obtained through their merchant/support workflow, but server must independently GET it and validate exact binding/provenance before accepting it. Matching amount/description alone is insufficient when multiple attempts can match; require authoritative linkage to this exact request. No invented bank search, request-ID lookup or provider charge creation to discover an unknown old outcome.

TerminalEvidence: {kind:"provider_terminal_no_charge"|"provider_cancelled",provider,provider_account_id,environment,configuration_version,provider_request_id,provider_reference?:string,attempted_at,review_window_start,review_window_end,provider_case_reference,evidence_reference,evidence_sha256,terminal_outcome:"no_charge"|"cancelled",reviewer_statement}. All fields bind to stored exact attempt/request/provider/environment; no caller amount override. evidence_reference identifies a tenant-authorized immutable stored document or auditable provider support reference; hash is validated against stored evidence when a file exists, not blindly accepted from a textbox. Support reference without local file requires a documented human verification statement identifying the provider terminal confirmation and exact case/request/account/time window. Redact card/token/bank secrets. UI must let owner/admin open the evidence context, record the provider case, explain the decision and see immutable history; not a generic “I checked” checkbox.

release_with_terminal_evidence is staff-only plus existing money step-up, with nonblank reason and complete authentic provider terminal no-charge/cancelled evidence. A merchant dashboard showing no transaction, empty local ID, customer “I wasn't charged”, bank statement absence, old timeout or elapsed time is NOT sufficient. Evidence is human-reviewed external proof and is labelled reviewed manual release, not automatic provider verification/bank settlement. If authoritative terminal proof cannot be obtained, keep customer retry blocked and give the staff the documented support-case/review path; do not return a dead-end opaque fail. This is an operationally complete review route, not a promise that every unknown request can be safely released instantly.

Before release, reauthorize/relock/refresh and check for intervening provider receipt, submission ownership, refund/dispute or new resolution evidence. A webhook/receipt arriving during human review wins: record actual money and reject release. A provider fact arriving after a reviewed release is still recorded with current allocation and overpayment review, never discarded. Audited evidence, actor and exact amounts survive; no invoice economics/provider IDs or historical ledger rewrites.

## Retry and UX

Only released/proven-terminal attempt enables a new payment intent. A new retry uses a NEW attempt ID/idempotency key and current invoice balance/version; never reactivate or mutate the cancelled attempt. Old tokens/client secrets/dispatch requests must fail after terminalization; actual late provider facts still reconcile. can_retry is false while the SAME requested funds have unresolved provider outcome or a blocking financial review; retain existing permitted independent partial-payment behavior only when it cannot retry the unknown amount or bypass its reservation. Do not present a full-invoice retry when only part is allocatable.

Customer: concise “Checkout started” before proof, “Transfer reported” for explicit Zelle assertion, “Payment received” only for verified receipt. One primary decision/notice, exact pending amount, cancel confirmation, checking/error feedback, safe retry button after resolution and persistent history notice. Staff: exact attempt controls, not-sent reason, check status, missing-reference evidence/case review, authoritative outcome and current balance. Never silently issue a refund or label a request cancellation as cancelling a bank transfer. Preview desktop/mobile with new fictional fixture records before deployment; no actual production clicks on resolution/charge/report/confirm.

## Final wire schema (required implementation interface)

ResolutionProjection is REQUIRED (not optional) on every PaymentAllocation row returned by existing customer, guest and staff allocation-page endpoints. It is the DTO above excluding nested settlement; actions includes required booleans cancel_unsent/check_provider_status/request_review/release_with_terminal_evidence/record_late_receipt, default false when unsafe or unauthorized. requested_principal/reservation_amount are authoritative money strings, versions integers; block_reason and resolution_notice nullable; review_status always present. Unsupported rail/legacy ambiguity returns review_required with disabled unsupported actions and a safe reason, never guessed actionable defaults. It contains no provider secret/case/private document fields. This is one batched evidence projection per existing page; do not issue a request for each activity row.

Mutation success returns existing PaymentAttemptResponse extended with required resolution:ResolutionProjection; existing settlement field supplies updated authoritative totals. request_review is a committed review request, not release; unknown provider check returns its current authoritative projection with can_retry=false and explicit result state rather than a fake cancellation success. Conflict uses detail:{code,message,current_attempt_version?,current_settlement_version?}; frontend refreshes its existing allocation/summary queries. No settlement nested inside resolution is required.

Authenticated GET /payments/attempts/{id}/resolution/read is staff-detail-only under canonical money permissions and returns {resolution:ResolutionProjection,binding:ResolutionBinding,evidence_requirements:EvidenceRequirements,history:[ResolutionHistory]}. Guest optional read detail is POST /invoice-access/attempts/{id}/resolution/read {token} and is strictly read-only, returning {resolution} only. Customer normally needs no extra read because allocations include it. Guest mutation POST /invoice-access/attempts/{id}/resolution {token,...command}; never GET-with-body or URL query token. Mutation command Idempotency-Key must be8–200characters, reason max1000; role/access checks occur before disclosing replay/details.

ResolutionBinding (staff-only server-built): {provider:"stripe_connect"|"quickbooks_payments"|"manual",provider_account_id:string|null,environment:"sandbox"|"production"|null,configuration_version:int|null,provider_request_id:string|null,provider_reference:string|null,attempted_at:ISO timestamp,requested_principal:string,provider_charge_amount:string,currency:"USD",evidence_context_sha256:string}. Every value comes from stored immutable binding/known dispatch evidence, not browser defaults. Missing historical values are null and accompanied by evidence_requirements/block_reason; never substitute current config/environment or invent a request ID. Provider request ID may be derived only from the exact historical code protocol proven for that attempt (e.g. stored QBO deterministic protocol), not a convenient guessed browser key.

EvidenceRequirements: {can_submit_terminal_evidence:boolean,requires_provider_case:boolean,requires_document:boolean,allowed_kinds:["provider_terminal_no_charge","provider_cancelled"],missing_binding_fields:[string],message:string}. Server determines these. Defaults: can_submit_terminal_evidence=false until the exact attempt binding and privileged review are valid; requires_provider_case=true; requires_document=false for a support-reference/human-verification route, true when claiming uploaded-file evidence. Human statement/case route does not pretend an attachment exists. ResolutionHistory staff records {event_id,action,occurred_at,actor_display,reason,proof_kind,evidence_reference?,provider_case_reference?}; customer uses only audience-safe resolution_notice and existing activity, not these private fields.

TerminalEvidence binding fields are copied read-only from ResolutionBinding; add evidence_context_sha256 to bind the reviewed exact server snapshot. provider_request_id is optional/null when the historical protocol cannot establish one; the provider's terminal support confirmation must instead unambiguously bind the known reference/request context/account/environment/time/amount. If that cannot be established, evidence_requirements disables release with a clear reason/support action. No account/env/provider/version defaults are typed by frontend. Human inputs: kind, provider_case_reference, evidence_reference, evidence_sha256 only for a real stored file, terminal_outcome, reviewer_statement, review_window_start/end. Server validates immutable evidence object ownership/hash or documented human case verification, fresh binding hash and all prior checks. Do not trust an arbitrary hash as a file proof.

No separate attach-known-provider-ID action is included in V1. UI must not offer a button promising automatic recovery/linking of an unknown charge. A provider reference may be entered only as part of the privileged terminal-evidence case; if it refers to a retrievable object, server must perform exact-bound GET validation before any release and deny on captured/ambiguous/mismatched money. Attaching a reference is not by itself terminal proof. Known-reference status checking remains check_provider_status for already bound objects. Additional automated reference recovery would require its own frozen proof contract.

Combined GET /payments/attempt-review-queue response {rows,next_cursor}, same bounded cursor/limit shape as the existing Zelle queue. Rows retain invoice_id,repair_order_id,display_invoice_number,customer_id,customer_display_name,principal_amount,attempt_id?,settlement_id?,settlement_version?,created_at,reported_at?,report_status,review_mode,can_confirm and add kind:"canonical_card_attempt"|"canonical_zelle_attempt"|"legacy_zelle_submission",rail:"card"|"zelle",resolution:ResolutionProjection|null. resolution is required nonnull for canonical rows; null only for genuine legacy invoice rows. review_mode canonical_attempt opens existing StaffSettlementDialog(invoiceId) then exact attempt row; legacy_invoice preserves existing legacy handling. can_confirm does NOT grant manual card-receipt authority; card actions come from resolution and provider verification only. Include unresolved card checkout/status/review and Zelle assertions/review requests, dedupe legacy compatibility rows, retain valid archived-parent collection/billed-customer handling and payment-role gate. Existing GET /payments/zelle-review-queue remains unchanged/backward compatible and Zelle-only. No new top-level navigation; current Review surface switches to this combined query and preserves invoice dialog placement. All queue/detail reads are no_autoflush/no-init/no-provider-IO.

## One-time terminal-evidence authorization scope

release_with_terminal_evidence requires the NEW distinct destructive one-time scope payments.attempts.resolve through existing payment step-up grant tables/mechanism (scope is stored string; no schema migration). It is not inherited from payment_sources.manage/read/platform controls/force-void. Current tenant owner/admin payments authority is required both when issuing and consuming the grant. Frontend requests this exact scope with existing password step-up flow and sends the grant as X-Step-Up-Authorization on the resolution command. WorkOS/passwordless accounts without supported verification receive an explicit safe unavailable route; no bypass or fake password grant. Cancellation/status-check/review-request retain their explicit action authorization; no new unnecessary password step for viewing or local unsent cancellation.

An already committed same-key/same-hash command replay reauthorizes identity/scope ownership and returns the existing resolution without requiring a fresh consumed grant. A new/changed command cannot reuse the consumed grant; conflict never silently reauthorizes another release. Grant consumption, immutable command audit and local release are atomic. Source history captures actor and grant authorization without exposing grant/token material in DTO/evidence/logs. Test scope separation, expiry, wrong identity/tenant, consumed-grant replay and new-command rejection.
