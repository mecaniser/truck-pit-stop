# DB-COMMS-017: authenticated incoming MMS image viewing

Status: revised implementation contract, 2026-10-22; narrow provider redirect correction pending implementation and fresh independent gates. Accountable owner: Backend & Integrations; contract owner: Architecture & API Contracts. Product & Delivery Lead coordinates. High-risk lane because new sensitive-media retrieval crosses staff authorization, tenant and provider-credential boundaries. Independent QA and Security gates required.

## Outcome and approach

Staff see incoming MMS images inside the existing conversation. Preserve the current reply route, received time, caption, deduplication, consent behavior and notifications. All three SMS automation/routing/recovery flags remain false. No outbound MMS, provider configuration, forwarding changes, OCR, image-content extraction or automatic processing.

Use lazy authenticated retrieval, not ingestion or permanent image storage. Existing messages already retain account, binding, provider message/conversation identities and aliases; existing attachment receipt bodies identify candidates without migrations. `communications_service.message_json` currently returns text only; `CommunicationsPreview.tsx` renders the shared message bubbles. Existing upload data-URI patterns are unsuitable for provider media: they trust declared types and would persist bytes. Use Pillow already installed, following the stronger validation approach in `external_service_receipt.py`.

Provider evidence: [CallRail API documentation](https://apidocs.callrail.com/#retrieving-a-single-text-conversation) documents conversation retrieval with paginated messages, message identity/type and media URLs. Media retrieval requires the API key; returned URLs must not be stored and should be refreshed when needed. This contract relies on fresh conversation retrieval and fails visibly if the provider no longer retains the media. It does not promise indefinite retention.

## Additive inbox contract

Existing message JSON adds `has_attachments: boolean`, default false in frontend compatibility mapping. True only for incoming CallRail messages whose body ends with the exact existing attachment receipt notice and which retain provider binding/account/conversation/message identity. No upstream call during inbox serialization. This is a candidate indicator, not a promise that the image remains available. Do not remove or rewrite persisted caption/notice text.

`GET /api/v1/communications/conversations/{conversation_id}/messages/{message_id}/attachments`

Authenticated manifest response:

```json
{"items":[{"index":0,"kind":"image"}]}
```

Indices are provider attachment slots, integer 0 through 9. The browser receives neither provider identities nor URLs. Empty `items` means no retained media. Manifest discovery must not download image bytes. The frontend constructs local content routes from conversation/message IDs and index, never from provider strings.

`GET /api/v1/communications/conversations/{conversation_id}/messages/{message_id}/attachments/{index}`

Returns bounded, decoded and re-encoded raster bytes with authoritative `Content-Type: image/png`. PNG-only output remains within the additive browser JPEG/PNG raster contract; input formats remain JPEG, PNG, WebP and GIF. The application response never redirects or exposes a provider URL, bucket locator, data URI or credential-bearing query. The bounded backend-only redirect allowance below does not change this browser contract. Headers on success and failures: `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`. Content-Disposition uses an application-generated inline filename. Do not reuse upstream headers.

Errors use existing `{detail:{code,message}}`: 404 `attachment_not_found` for missing/foreign/deleted message, inconsistent binding/provenance or absent index; 403 existing messaging-access denial; 422 `attachment_unsupported` for unsupported/invalid raster; 413 `attachment_too_large`; 502 `attachment_unavailable` for sanitized provider rejection/invalid response/disallowed redirect; 504 `attachment_timeout`. No upstream response body, URL, phone, credential or image contents in errors or logs. Authentication failures follow existing dependency behavior.

## Authorization and identity

On BOTH routes call the same current-user dependency, `authorize` and `thread_for` as existing inbox detail. Select the nondeleted message by tenant + thread + ID; require inbound CallRail and matching nondeleted enabled binding belonging to that tenant/account. Resolve a nondeleted conversation mapping for that message's stored binding and thread, not whichever binding is now selected for sending. Validate mapping/customer/inquiry identity; reading remains allowed for opted-out contacts. Do not call sending policy or require consent to view a received image. Fail closed on changed contact identity or disabled binding; do not mutate routing to repair it.

Retrieve only the stored provider conversation, using the binding's dedicated credential reference. Validate returned conversation ID, company and customer contact against stored context. Identify exactly one provider message using trusted stored numeric/resource aliases; match incoming direction, original timestamp and caption. When matching through a media resource ID, extract it only from an already validated API path and require an exact stored SCI identity. Never match by timestamp or body alone. Never infer a historical receiving number from a conversation's current tracker. The local message's binding/from/to provenance remains authoritative. Support the pre-existing receipt without replay, migration or backfill.

## Network and decoding boundary

Construct conversation request URLs on literal `https://api.callrail.com`; validate account/conversation identifiers before path assembly. Stream JSON with a 2 MiB cap; paginate at most 10 pages of 100 messages, reconstruct page requests locally, and reject inconsistent pagination. Never follow provider pagination URLs. Stop once the unique message is established; fail closed if ambiguity is observed. Cap media slots at 10 and validate their full list before exposing indices.

Every media URL must parse to HTTPS, exact host `api.callrail.com`, default port, no userinfo, fragment or query, and exact `/v3/a/{bound_account}/text-messages/{trusted_SCI}/media/{index}`. Require media SCI to agree with stored resource alias when present. Reject encoded path tricks and mismatched account/index. This is not an arbitrary URL proxy. Provider credentials are sent only to that exact origin. Set `follow_redirects=False` on every client. Conversation discovery rejects every redirect. For the exact identity-validated media request only, accept a direct 200 image or exactly one 302 through the restricted signed-object policy below. Reject 301, 303, 307, 308, missing/duplicate Location and every other redirect target; never expose Location or widen hosts opportunistically.

### Restricted signed-object redirect policy

Live acceptance of a user-supplied ordinary photo established that the identity-validated media endpoint returns 302 to `calltrk-mms-media-prod1.s3.amazonaws.com`. No redirect was followed during diagnosis and no image bytes were obtained. This observed origin replaces the earlier all-redirect denial only for this narrow case; it does not authorize arbitrary S3/CDN access. The prior protected release remains deployed but actual inline provider-image acceptance is unresolved until this correction passes gates and runtime acceptance. The prior verification-code image remains excluded.

The validated account/message/index CallRail endpoint, with its authenticated response, is the authority for the downstream locator. Neither browser input, stored URL, manifest URL nor a caller-supplied host can select the object. Validate Location before any downstream request, and accept only an absolute URL with literal HTTPS scheme and exact netloc `calltrk-mms-media-prod1.s3.amazonaws.com`. Reject explicit ports (including 443), userinfo, fragment, backslash, control characters, whitespace, malformed percent escapes and any alternate/suffix/case/trailing-dot host. Limit the complete locator to 16 KiB, query to 12 KiB and path to 1024 characters. The observed object shape is one nonempty root key: `/[A-Za-z0-9_-][A-Za-z0-9_.-]*`; reject extra slash, percent-encoded path, standalone dot/dotdot and traversal forms. This policy does not infer any tenant or message identity from an opaque object key.

Accept only SigV4 query keys observed from this response: `X-Amz-Algorithm`, `X-Amz-Credential`, `X-Amz-Date`, `X-Amz-Expires`, `X-Amz-Security-Token`, `X-Amz-Signature`, `X-Amz-SignedHeaders`, `response-content-disposition`, `response-content-type`. Require one of each, reject duplicate/unknown/empty keys, malformed encoding and decoded control characters. Decode query values once only for validation; preserve the original signed URL for the request, never rebuild/re-sign it or use response overrides as application headers. Require `AWS4-HMAC-SHA256`; a 64-character lowercase hex signature; nonempty bounded credential/token values (credential at most 512, token at most 8192 characters); credential scope `ACCESS_KEY/YYYYMMDD/REGION/s3/aws4_request` with restricted alphanumeric/underscore/hyphen components; scope date equal to the signing date; and signed headers exactly `host`, so no forwarded application header participates. Validate UTC signing timestamp and bounded positive decimal expiry, reject expired URLs and signing dates over 60 seconds in the future. Observed expiry is 300 seconds, with signed headers exactly `host` and JPEG response type; maximum accepted expiry is 300 seconds; do not extend the URL lifetime or retry with an expired locator. `response-content-type` must be an allowed raster type; content-disposition is at most 1024 characters and is never reflected. Reject unsupported signing shapes rather than weakening validation.

Fetch the accepted object with a NEW dedicated HTTP client: no CallRail Authorization, application bearer token, cookies, cookie jar copied from the first client, HTTP auth, Request-From, Referer or inherited client headers. Disable environment-derived proxy/auth configuration (`trust_env=False`), set `follow_redirects=False`, and send only application-selected Accept/Accept-Encoding headers. Do not construct headers from Location or provider response. Any response other than 200, especially a further 3xx, fails closed; do not follow, resolve, probe or return the second Location. Both clients close on all outcomes. Close the 302 response before starting the object request.

Retain the SAME overall 20-second budget across discovery, CallRail media request, one object request and decode; preserve streaming 5 MiB cap, strict MIME/byte agreement, decompression/dimension limits, re-encoding and private response headers. Reject compressed content before decoding, including on the object response. No durable locator storage, cache, asynchronous retry, additional origin, media mutation or new provider credential. The existing request-scoped ContextVar HTTP/httpcore log suppression covers the entire chain including client construction, response headers, signed query, exception/cancellation and closure. Sanitize all errors without interpolating the request/response/exception or Location. Preserve unrelated concurrent-request logging and reset context only after all private transport work ends.

Required negative tests: untrusted origin/suffix/IP/localhost/userinfo/port/fragment/control/backslash/encoded path/traversal; oversized locator/query/path; unknown/duplicate/missing query key, malformed encoding or signing shape, invalid credential scope/date, expired/too-long/future expiry, signed headers other than host; 301/303/307/308 from CallRail; any second redirect; downstream nonimage/oversize/encoded/malformed/dimension/timeout failures. Positive synthetic SigV4 302 fixture must prove exactly one downstream GET and decode. Assert its headers contain no Authorization, Cookie, Referer, Request-From or inherited auth, even if CallRail returned Set-Cookie or environment proxy/auth is configured. Capture INFO/DEBUG httpx/httpcore logs through success, rejected Location, timeout, cancellation and second redirect to prove no upstream auth token, signed query, security token, object key or Location leaks; concurrent ordinary logs must remain present. Repeat tenant/message authorization and unchanged DB/reply/flag assertions.

Use explicit connect/read/pool timeouts and a 20 second overall request budget. A single manifest/content operation has bounded provider requests, no retries or background jobs. For bytes, stream with a hard 5 MiB input limit regardless of Content-Length, including chunked/encoded bodies. Check declared content type and actual raster decode agree: JPEG, PNG, WebP or GIF input only; reject SVG/HTML/PDF/HEIC, malformed files, decompression bombs, dimensions above 8192 per side or 25 million pixels. Decode only frame zero, apply EXIF orientation to the decoded pixels, and output a fresh static PNG, stripping EXIF/metadata and appended data. Do not perform a second lossy JPEG encoding pass. Cap encoded output at 10 MiB, without increasing the cap or resizing to evade it. A detailed phone JPEG below the 5 MiB input limit can expand beyond 10 MiB as PNG; return the existing graceful `attachment_too_large` error in that case. This explicitly trades some large-image availability for bounded output and avoids reproduced Pillow 10.1/libjpeg corruption in a tiny EXIF fixture; the original decoded/oriented pixels were correct and the failure occurred during final JPEG encoding. Treat that failure as evidence requiring this output correction, not a flaky test or justification to weaken image assertions. Fresh output-format and output-cap tests plus an independent gate remain required. Run decoding in a worker thread; no mutable global Pillow limit changes. Do not persist or log bytes, URLs, manifest provider response or keys; no shared media cache.

## Frontend lifecycle

Add optional `hasAttachments` to the shared message model. Render an image area only for candidates in the selected conversation. Fetch manifest and blobs through existing authenticated API client with `responseType: 'blob'` and AbortSignal; never put bearer tokens in image URLs. Load at most two blobs concurrently. Use object URLs for `<img>` and revoke them on replacement, unmount, thread/session change and stale completion. Include auth session epoch in lifecycle isolation; prior-shop responses must never display after account switch. Clear images immediately on session change.

Show loading, inline constrained image thumbnails (`object-fit: contain`) and concise unavailable/unsupported state with a manual Retry action. Clicking a loaded image opens an accessible in-inbox dialog using the already loaded blob; do not initiate another fetch. Provide a labelled Close control, Escape dismissal, focus containment and focus restoration to the launching thumbnail. Closing or expanding must preserve the composer draft and reply route. Close and discard the dialog on thread/session changes. No automatic infinite retries. Use descriptive generic alt text, never inferred image contents. Preserve caption/timestamp and compose draft. The provider attachment notice may be hidden only in the rendered bubble once media is available; keep it/fallback when unavailable. No sender selector, reply-policy change, outbound upload or consent toggle. Existing plain SMS and non-CallRail bubbles are unchanged. Responsive layout must fit narrow viewports.
